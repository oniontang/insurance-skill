# 产品匹配推荐

需求在前，产品在后。本模块把客户需求翻译成产品形态，再从产品库中选出适配项。匹配结论只解决"讲什么、对谁讲"，具体数字一律以保险公司计划书为准。

## 一、需求分类 → 产品形态映射

先按 `kyc.md` 的需求分类确认客户主需求，再查下表（满足主需求优先，最多匹配 2 个产品形态，不贪多）：

| 需求分类 | 客户典型表述 | 首选产品形态 | 备选/组合 |
|---------|------------|------------|----------|
| 保障缺口型 | "万一得大病怎么办""家里就我一个挣钱" | 重疾险 + 医疗险 + 定期寿险 | 保障配齐后再谈理财 |
| 教育金规划 | "孩子大学要花不少""想给孩子留点钱" | 年金险（教育金形态）/ 增额终身寿 | 减保规则灵活者优先 |
| 养老补充 | "退休以后光靠退休金不够" | 年金险（养老金形态，领终身） | 增额终身寿（重灵活） |
| 强制储蓄 | "钱总存不住""想攒下第一笔钱" | 增额终身寿（缴费期短一些） | 年金险 |
| 资产传承/隔离 | "钱想定向留给孩子""婚姻财产 concerns" | 增额终身寿（指定受益人） | 年金+万能架构；涉及复杂情况建议客户咨询专业法律/税务人士 |
| 锁利/跑赢利率下行 | "利息越来越低，钱放哪" | 增额终身寿 / 分红险 | 按风险偏好定 |
| 博取更高收益 | "保底太低，想搏一搏" | 分红险 / 万能险（账户） | 必须先确认客户理解非保证部分 |

匹配时的硬约束（任一不满足则该产品出局）：
1. **预算约束**：年缴保费 ≤ 客户年结余的 10-15%（保障型优先占用）。
2. **流动性约束**：客户短期（3-5 年内）确定要用的钱不进理财险。
3. **健康约束**：保障型产品需通过健康告知，健康异常客户先核保评估。
4. **年龄约束**：对照产品库中各产品的投保年龄上限。

## 二、产品库加载规则

1. 产品库文件位于 `assets/product-library.md`。**先检查该文件是否已被用户填写**（含真实产品条目，而非模板占位符）。
2. **已填写**：从产品库中按映射表筛选，只推荐库内产品，引用库中的卖点与话术要点。
3. **未填写**：向用户说明"产品库还没有录入产品，我先按产品形态给出匹配逻辑与讲解框架"，并引导用户按 `assets/product-library-template.md` 格式录入主营产品（1-2 分钟一个条目）。禁止虚构具体产品名称与收益。
4. 用户提供的公司口径与产品库冲突时，以用户提供的最新口径为准，并建议其更新产品库。

## 三、匹配流程五步

1. **确认主需求**：来自 KYC 需求点总结（不明确的先回 `kyc.md` 补挖）。
2. **过硬约束**：预算、流动性、健康、年龄四道闸逐一核对。
3. **选形态**：按映射表确定 1-2 个产品形态。
4. **选产品**：在产品库该形态下比较（优先级：卖点与客户痛点契合度 > 缴费期匹配 > 服务资源）。
5. **给结论**：输出匹配矩阵，交由用户用计划书做最终测算。

## 四、匹配结论产出标准

1. **客户需求回放**（2-3 行，含客户原话）
2. **匹配矩阵表**：候选产品 ×（适配的需求点、适配理由、需注意的点）
3. **首选推荐 + 理由**（为什么是它而不是备选，用客户听得懂的语言）
4. **讲解切入建议**（衔接 `proposal.md` 的五步讲解顺序，指出该产品最打动这位客户的一个点）
5. **合规提醒**（涉及分红/万能必须注明非保证部分；提示"以官方计划书为准"）
