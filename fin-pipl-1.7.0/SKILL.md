## 🚀 快速开始

> ⚠️ **结论必须基于真实作答。** 只指定 `--scenario` 而不提供作答来源时，程序会直接拒绝执行（退出码 2），不会用空答案生成报告。

```bash
# 0) 先看看报告长什么样：用内置样例作答直接出报告（不需要先答题）
python3 scripts/fin-pipl-check.py --scenario banking --demo
python3 scripts/fin-pipl-check.py --scenario banking --demo --format html --output demo.html

# 1) 交互式自查（推荐）：逐题作答；结束后可把答案存盘
python3 scripts/fin-pipl-check.py --scenario banking --interactive
python3 scripts/fin-pipl-check.py --scenario banking --interactive --save-answers answers-banking.json

# 2) 用答案文件作答：适合复核复跑、批处理与 Agent 调用
python3 scripts/fin-pipl-check.py --scenario banking --input answers-banking.json

# 3) 出具报告（Markdown / JSON / HTML）
python3 scripts/fin-pipl-check.py -s banking --input answers-banking.json --output report.md
python3 scripts/fin-pipl-check.py -s banking --input answers-banking.json --output report.json --format json
python3 scripts/fin-pipl-check.py -s banking --input answers-banking.json --output report.html --format html

# 4) 合规台账：自动与上次对比，输出整改进度（台账跨次累积）
python3 scripts/fin-pipl-check.py -s banking --input answers-banking.json --ledger ledger.jsonl

# 场景可选：banking（银行）/ securities（证券）/ insurance（保险）/ payment（支付）
python3 scripts/fin-pipl-check.py --list-scenarios   # 列出全部场景
python3 scripts/fin-pipl-check.py --version          # 查看版本
```

### 一键样例（`--demo`）

`--demo` 用**内置样例作答**跑一遍，直接看到一份完整报告——四种状态（✅ 通过 / ⚠️ 警告 / ❌ 未通过 / ➖ 不适用）在四个场景里都能看到，适合第一次接触时先了解输出形态。

```bash
python3 scripts/fin-pipl-check.py --scenario banking --demo
```

```
==================================================
⚠️  DEMO — 样例报告，非真实检查结果
==================================================
🏦 Fin-PIPL 合规检查报告
场景: 银行业务
结果: 6/8 通过, 1 警告, 1 未通过（另有 2 项不适用）
合规率: 75%（按 8 项适用项计）

※ 以上基于**内置样例作答**，仅用于预览报告形态。
  它不是对任何机构的检查结论，请勿作为合规依据，也不会写入台账。
```

**边界（刻意设计，不是限制）**：

- 样例是**构造出来的**，不含任何机构信息，**不是检查结论**，不得作为合规依据；
- 报告（Markdown / HTML / JSON）与控制台**均带 DEMO 标记**；
- `--demo` 与 `--ledger` **互斥**（退出码 2），样例数据**不可能进入真实合规台账**；
- `--demo` 与 `--interactive` / `--input` 亦互斥——三者只能选其一。

> 想得到**真实结论**，请用 `--interactive` 或 `--input`。`--demo` 只负责让你先看见形态。

### 合规台账与整改进度（`--ledger`）

`--ledger FILE` 把每次结果追加进一个 **JSONL 台账**，并在同一次运行里**读取该场景的上一次记录做对比**：

```
📈 与上次相比（上次：2026-09-26 13:33:04，合规率 75% → 75%，+0 个百分点）
  ✅ 新增通过 1 项：征信信息 - 查询与报送合规
  ❌ 新增未通过 1 项：个人金融信息 - 分类分级合规
  ➖ 状态未变 8 项
```

- 首次运行会创建台账，显示「上次：—」，无对比基线
- 对比按**检查项逐项**进行，不只看合规率——上例合规率没变，但实际修好 1 项、新增 1 项问题
- 台账跨场景共用一个文件，**按场景各取各的上次记录**，互不干扰
- 台账为一行一条 JSON，可人工阅读、可 grep、可入版本库；**行结构被破坏时会报错并退出**（退出码 2），不会静默放过
- 不传 `--ledger` 时**不写任何文件**，行为与不带该参数时完全一致

### 答案文件格式

`--save-answers` 生成的文件可直接被 `--input` 复用；也可以手写：

```json
{
  "scenario": "banking",
  "answers": {
    "has_privacy_notice": "y",
    "consent_method": "manual",
    "sensitive_items": ["biometric"],
    "has_loan_authorization": false
  }
}
```

值可用 `y`/`n`、`true`/`false`，或按题目提示给出选项值（如 `consent_method` 的 `manual`/`pre_checked`）。
缺少作答时，程序会逐条列出缺哪些问题 id 并退出，不会据此给出结论。

## 🔍 检查项概览（34 项）

> 下列 34 项均由脚本实际执行，与代码一一对应（银行 10 / 证券 8 / 保险 8 / 支付 8）。每项由若干问答项支撑，全场景共 123 个问答项。

### ➖ 关于「不适用」（N/A）

判据**只有一条**：

> **该检查项针对的业务活动或技术机制，在本机构不存在 ⇒ 判「不适用」。**

例如未开展再保险、不涉及跨境传输、不使用自动化决策、不做收单——这些是「没这项业务」，不是「没做好」。

与之相对，**业务存在但措施未落实仍是警告或未通过**（如应加密未加密、应告知未告知）——那是应做未做。

**不适用项不计入合规率分母**，报告单独列出。这是为了避免用「没检查」冒充「合规」——
否则未开展的业务会白白拉高合规率，等于虚报。

**怎么触发**：每个可能不适用的检查项都有前置的「是否涉及」问题（如「是否涉及再保险安排？」「是否使用自动化决策？」）。
在该问题上答 `n`，该项即判不适用。提问时按实际情况回答即可，不需要额外操作。

### 📚 关于法规引用

引用**只写到能够核对的层级**：

- **《个人信息保护法》**：写到条文号（如 `PIPL Art.24`），条号与内容已逐条核对中国人大网公布的**法律全文原文**；
- **行业标准与其余法规**（JR/T 0171、JR/T 0197、《征信业管理条例》《保险法》《金融产品网络营销管理办法》等）：**只写名称，不写章条号**——章条号无法从本包内核实，宁可不写。

> 如果你看到某处引用了本包无法自证的章条号，请当作缺陷反馈。

### ✋ 关于「能不能真的检查到」

**本工具是自述式问卷**——它拿不到你的内部系统、文档库或留存台账，所以**每一项都是"你说，我按规则判"**，不是核实。

这一点在「个人信息保护影响评估」上尤其要讲清：「评估报告与处理情况记录留存不短于三年」是**事前**评估时就该设定、并长期履行的义务。**在事前评估的当口，三年尚未届期，任何工具都核实不了"是否已留存三年"**——能问的只有：

- 是否**已设立**不短于三年的保存期限，并**照此留存**？

答 `y` 是**你的自述**。工具做的只是：把这条义务**摆到台面上**、给出判定口径、并留下记录。**不要把它读成"工具已核实合规"。**
